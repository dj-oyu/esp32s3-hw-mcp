## 2. ストール（§4）

- `EE.VLD.128.IP` / `EE.VLDBC.16.IP` / `EE.LDXQ.32` / `EE.VLD.L.64.IP` の def 段は **2 (M)**。
  つまり**ロードした直後に使うと 1 サイクル止まる**（:557）。
- TRM 1.7.1 の `D = max(SA − SB + 1, 0)` を Table 1.7-2 に当てる（:549-566）。
- **計算で消えるはずのストールが消えない**ときは、間に独立命令を挟む（:574 の「索引ロードの書き先を
  交互にする」例）。

## 3. 索引ロード（表引き）の値段（§3, §3.5）

- PIE で**索引ロードできるのは `EE.LDXQ.32` だけ**、しかも **1命令で1レーン**（:19, :44）。
  8要素引けば 8 命令、2表なら 16 命令。**`EE.LD.QR` は索引ロードではない**（`load128(as + imm)`）。
- 高いのは命令の値段ではなく**本数**（:76-82。アドレスが散っていても、同じレジスタの別レーンでも同じ）。
- **表そのものに定数を畳む**のが有効（:125 の正弦表 `(sine[i]/6)*16 - 180*16`、
  波カーネルの `lo | (hi << 16)` ＋ `EE.VUNZIP.16`）。
- 近似に置き換えられるなら置き換える: 正弦表を放物線近似（`u(128-|u|)` ＋ 補正項1つ）にして
  **16本の `ldxq` ＋ 2本の `vunzip` ＋ 2本のマスクが消え、62 → 40命令 / 1.06 → 0.89 ms**（:48）。
  ただし**ビット一致は捨てる**。

## 4. スカラー側の値段（§3.7、:190-290）

| 演算 | 実測 | 備考 |
|---|---|---|
| ハードウェア整数除算 | **約 16〜18 サイクル** | 逆算（:261）。「シフトや逆数乗算に置き換えると速くなる」は**測定差なし** |
| `__divsf3`（float 除算） | **55〜67 サイクル** | 長期の推定 150〜250 は 4 倍外していた（:245-250, :505） |
| `sqrtf` | **174〜188 サイクル** | 同上 |
| `floorf` / `ceilf` | **約 78 サイクル** | 条件付きで `ifloor`/`iceil` に置換可（§3.12） |

- **`-mlongcalls` で `l32r` + `callx8` に割れる**ので、逆アセンブルを grep しても `__divsf3` は見えない
  （ROM の絶対アドレス `40002274` を指す。`nm` にも並ばない。:201）。**「grep して無い」を根拠に
  「呼んでいない」と結論しない**（実際は16本あった）。
- **FPU の除算・平方根の種命令はこの石に載っているが GCC が出さない**（§3.13、:532-548）。

## 5. 書くときの落とし穴

- **`loopgtz` の本体は 256 バイトまで**（§7、:612-619）。
- **インライン asm で定数表を歩くポインタには early-clobber `"=&a"` が必須**（§6、:594-611）。
  `"+a"` だと GCC が別オペランドと同じレジスタを割り当て、巻き戻しの `mov` が消えることがある。
- **PIE はコプロセッサ3 なので ISR 内では使えない**（§1、:9）。タスク切替で q0〜q7 が退避・復元される。
- **16bit レーンのシフト命令が無い** → SAR を固定して `EE.VMUL.S16/U16` の定数乗算で表す。
  左シフトは ×16 まで（§2、:25-40）。
- **`EE.SRCMB.S16.QACC` のシフト量は SAR ではなく AR から来る**（§8）。
- **128bit アクセスは下位 4bit を黙って 0 にする**（§5、:586-592）。整列違反は例外にならない。
- GCC は q レジスタを clobber リストに受け付けない（`unknown register name 'q0'`）。既存カーネルは
  clobber を書かない規約で回っている。

## 6. 最適化の判断（測る前に読むところ）

- **拒否テストの経済学（§3.8、:294-393）**: 「visit の N% を落とす」は「時間の N% を落とす」ではない。
  判定が判定している仕事より高い領域がある（:323-338）。
- **overlay の二つの罠（§3.9、:394-433）**: 1 フレームに 17 回呼ばれる、**重なる走査は本数に比例しない**
  （実測 4 本で 2.06 倍、:422-424）。
- **半径は歩幅で買う／区間は形ではない／「計器が黙る」四つの形（§3.10、:434-472）**。
- **ピクセルに見えて、フレームに 1 回でよかった除算（§3.11、:473-514）**: `1.0f/a` が
  (部品, 帯) ごとの定数だった → `petal_reciprocals` へ巻き上げ。visit あたり 4.5〜5.4 本の除算が消えた。
- **`floorf` は条件付きで置き換えない（§3.12、:515-548）**: 「引数が非負だからキャスト」ではなく、
  前提の要らない `ifloor`/`iceil` を作る（総当たりは `tools/test_flower_floor.c`）。
- **命令数はサイクルを予測しない（§3.8、:358-374）**: レジスタが溢れている領域では逆転する。
  「最適化とその計測を同じコミットに入れない」。

## 7. 計測の作法（§9、:663-731）

- **同じカーネルがビルド間で 15% 動く**（:718。i-cache 16KB が両コア共有で、関数配置が変わると
  当たり方が変わる）。**数%の差を主張するには同一バイナリ内のスイッチで A/B を取る**。
- **`-Os` では `memcpy` が関数呼び出しのまま残る**。バイトスワップを 32bit 化した版は
  16.5 → **24.2 ms に悪化**（:730）。「明らかに速いはず」の変更は必ず測る。
- **計測スクリプト自身が測定対象を変える**（:706。再描画を促す Enter が効果音を鳴らし 3〜4割の水増し）。
- **共有ツリーでは比較ビルドが同じソースかを検査する**（:726。`find main components apps -newermt`）。
  変更していないビルドのサイズが動いたら、それは自分のツリーではない。
- **単独計測と実動作では 3〜4 割違う**（:108-116）。µs 換算は下限としても信用しない。
- 測定対象の設定値（SPI クロックなど）は**起動時にログへ出す**（:726。`board.c` の `LCD SPI %d Hz`）。

## メモリ側（同プロジェクト `CLAUDE.md`）

- **DRAM は約 334 KiB**（PSRAM なし）。ホーム画面の空きヒープは実測 **274 KiB**（`idle_free=280,932`、
  Wi-Fi リンク後）。静的 DIRAM を 197,847 → 111,383 B まで削った結果で、**削減のたびに動く**
  （`CLAUDE.md:84`、`docs/vm-L2-design.md:717`）。
- **Wi-Fi をリンクするだけで空きヒープが約 37 KiB 減る**。一度起動すると約 4.8 KiB は戻らない
  （`esp_netif_deinit()` が IDF v6.0.1 で `ESP_ERR_NOT_SUPPORTED`。`CLAUDE.md:91`）。
- JS ゲストの上限は **144 KiB**（`CLAUDE.md:84`）。ただし `docs/vm-L2-design.md:717` は 160 KiB と書いて
  おり、**この2つは一致していない**（どちらが現在かは断定しない）。
- 転送の実測: ホーム画面 `send=15.68 / 15.47 ms`（`docs/pie-simd.md:686-687`、ただし同 :702 が
  「この表の絶対値は数割高い」と断る）、修正後・SPI 80 MHz で `send=7.67 ms`（同 :702）。
