# 07 — PIE 実用サンプル（examples/）

`examples/` は、`data/` の知識（マニュアルの図と疑似コード、アセンブラ照合の結果）だけを使って
書き上げた手書き PIE アセンブリの例題集です。「知識 → ファームウェア」の向きの検証で、`data/` の
抽出（PDF → データ）とは独立に、**その知識で実際に何か動くものを書けるか**を試します。

## なぜ例題集なのか

`data/pie_instructions.json` には各命令の Operation 疑似コードが入っていますが、それは「読み取った」だけ
です。読解が正しいかを試す最良の方法は、疑似コードから手で書いたアセンブリを走らせて、同じ疑似コードから
独立に書いた参照実装と突き合わせることです。例題は 3 段で照合します:

1. 手書き PIE アセンブリ（`examples/firmware/main/ex*.S`）
2. ファーム内の C 参照実装（`main.c`、装置上で比較して `CHECK` 行を出す）
3. ホスト側の Python 参照実装（`tools/check_examples_log.py`、ログの入力から再計算）

3 が 2 と独立なのが要点で、2 と 3 が同じ誤解を共有していれば 3 は落ちませんが、**1 が疑似コードと違えば
必ずどちらかが落ちます**。

## 各例題が確定させること

### ex01: アドレス後置インクリメントの刻み（`data/pie_encoding_errata.json` の決着）

`EE.ST.ACCX.IP` の即値について文書が三通りに割れています:

| 出どころ | 主張 |
|---|---|
| 構文行の範囲 `-512..508` | 4 バイト刻み |
| アセンブラ（受け付ける値） | 8 の倍数のみ（＝8 バイト刻み） |
| Operation 疑似コード `as += imm8` | 1 バイト刻み |

アセンブラは 8 の倍数しか受け付けないので、`field=1`（4 バイト相当 / 8 バイト相当 / 1 バイト相当の境目）を
**生バイトで書いて**動かします。`ex01_raw_st_accx_field1` がその命令語で、`tools/asm_toolchain.py` の
エンコーダでマニュアルの図から生成したものを `.byte` として埋めてあります（逆アセンブルすると
`ee.st.accx.ip a3, 8` と出るので、ツールチェーン側は 8 バイト説）。

同じ関数で `EE.LD.ACCX.IP` も測ります（こちらは疑似コードに `{21{imm8[7]},imm8[7:0],3{0}}` と明記されて
いるので 8 バイトが予測、外れたら疑似コード側の欠陥）。

### ex02 / ex03: アキュムレータの向き

- `EE.VMULAS.S16.ACCX qx, qy` は 8 レーンの積を**合算**して ACCX（40bit）に入る → ドット積向き
- `EE.VMULAS.S16.QACC qx, qy` は 8 レーン**独立**のアキュムレータ（40bit×8）→ 8 並列向き
- 読み出しは `EE.SRS.ACCX au, as, 0`（`ACCX >> as[5:0]`、32bit 飽和）、`EE.SRCMB.S16.QACC qu, as, 0`、
  `EE.ST.QACC_H.L.128.IP` / `EE.ST.QACC_L.L.128.IP`

行列積と FIR はこの「合算」側だけで書けます。**Table 1.7-2 は VMULAS の ACCX/QACC 書き込みを `def` に
挙げていません**（特殊レジスタへ書く命令の扱いが表から漏れている）。したがってスタール見積りは
`EE.VMULAS` → `EE.SRS.ACCX` のハザードを 0 と予測します。実機の内側ループのサイクル数と比べれば、
この表の穴の大きさが数字で出ます（`ex02` は `cycles_us` 行を出します）。

### ex04: 実測段の装置上での再確認

`LD.QR` / `ST.QR` は Table 1.7-2 に**載っていない**ため、段は実測（`data/pie_timing_measured.json` の
`LD.QR` def = M、`MV.QR` def = E、`ST.QR` use = M）でしか決まっていません。ex04 はその結論を
「距離 0 で 1 サイクル、距離 1 以上で 0」という形で装置上で再確認します（計測ファームの 2000 反復
min-of-repeats とは別経路の検算）。

### ex05: 飽和の位置

`ACCX` は 40bit で飽和、`EE.SRS.ACCX` は 32bit で飽和。32000×32000 を 8 レーン × 200 回で
数学的和 1.6384e12 に対し 40bit 上限 2^39-1 = 549755813887 で頭打ちになることを、`>>9` 読み出し
（飽和しない位置）と `>>0` 読み出し（飽和する位置）の両方で確認します。Q15 FIR を書くときに
「いつ飽和するか」を数字で持っておくための例題です。

### ex06: FFT プリミティブ（多段は次の段）

`EE.FFT.R2BF.S16` の疑似コードは、`qx`/`qy` の各 64bit 半身を選んで
`op_a`/`op_b` を作る、という形になっています（sel2 でその選び方が変わる）:

```
sel2 = 0 : op_a = {qy[63:0],  qx[63:0]}      op_b = {qy[127:64], qx[127:64]}
sel2 = 1 : op_a = {qy[95:64], qy[31:0], qx[95:64], qx[31:0]}
           op_b = {qy[127:96], qy[63:32], qx[127:96], qx[63:32]}
qa0 下位4レーン = op_a[0..3] + op_b[0..3]    qa0 上位4レーン = op_a[0..3] - op_b[0..3]
qa1 下位4レーン = op_a[4..7] + op_b[4..7]    qa1 上位4レーン = op_a[4..7] - op_b[4..7]
```

`qx = qy = 8 個の int16 サンプル` とすると sel2=0 は
`[x0+x4, x1+x5, x2+x6, x3+x7, x0-x4, x1-x5, x2-x6, x3-x7]` を返します。これは実 FFT の第 1 段そのもの
ですが、**多段に積むには「段と段の間のレーンの並び」を先に確定させる必要があります**。並びが違ったまま
多段を書くと「動かない」しか分からないので、例題はプリミティブの一致で止めています。

次の段の手順:

1. `ex06` の 2 つのプリミティブ（R2BF の sel2=0/1、CMUL の sel4=0/1）を実機で一致させる。
2. sel2=1 の並びを使って「第 2 段の入力がどのレーンに来るか」を実測で確定する（`DATA` 行にレーンを全部出してある）。
3. 8 点実 FFT を組み、Python の DFT と比較する。段ごとに中間バッファを `DATA` で出す。
4. 32 点に拡張（同じ 2 命令の繰り返し。トゥイードル表は
   `tools/asm_toolchain.py` の符号化器と Python 側の同じ表から生成し、両者がずれないようにする）。

`EE.FFT.AMS.S16.*`（ステージ間の加減算とメモリ出入力を 1 命令にまとめた形）は、この並びが確定した
後でないと意味が読めないので触っていません。

## 第1回ランで確定したこと（2026-09-14、ログ `pie-examples-20260914T174138Z.log`）

機械可読版は `data/pie_examples_measured.json`（`example_measured_semantics` ツールが返す）。要点:

- **`EE.ST.ACCX.IP` の刻みは 8 バイト**。生バイトで `field=1` を書いて測ると LD/ST どちらも 8 バイト進む。
  つまり `data/pie_encoding_errata.json` の当該項目は「アセンブラが正しく、マニュアルの構文行（4刻み）と
  Operation（1刻み）が両方欠陥」で決着。**誤植ではなく実害のある欠陥**だった例。
- **`EE.FFT.R2BF.S16` のオペランド列は MSB 先**（左のフィールドが上位レーン）。これは文書からは一意に
  読めない部分で、sel2=0 の一致だけでは決まらなかった（sel2=0 は左右どちらの読みでも同じ結果になる）。
  sel2=1 を走らせて初めて決まり、MSB 先の読みで両方が実機と一致、逆の読みは反例が出た。→ 多段 FFT の
  段間レーン配置が書けるようになった。
- **128bit アクセスの下位ビット丸めは実害として再現**。素直に書いたスライディング FIR（`x + 2*n` を
  そのまま `EE.VLD.128.IP` に渡す）は 49 出力中 42 が誤りで、正しいのは 16 バイト境界に窓が乗る
  n = 0, 8, 16, 24, 32, 40, 48 の 7 点だけだった。「窓を 16 バイト境界に切り下げる」モデルは実機の 49 出力を
  完全に再現する。カーネルを直す方向は 2 つ（境界に揃えた窓を渡す／`EE.LD.128.USAR.IP` + `EE.SRC.Q` の
  ファネル経路）で、後者のオペランド順は次のランで決める。
- **ACCX は本当に飽和する**。数学的和 1.6384e12 に対して 549755813887（2^39-1）で止まる。Q15 FIR の
  スケーリングを設計するときは「飽和する」前提でレンジを決める必要がある。
- **計測ファームの結論が別ハーネスで再現**。`LD.QR` のインターロックは距離 0 で 1 サイクル、距離 1 で 0。

失敗の原因が全部「こちら側」だったのは、期待値をマニュアルの疑似コードから手で作っている以上避けられない
コストで、それを見つけるために C 参照と Python 参照を別々に書いている。**装置が文書と違う**ときだけ
知識が増える、というのがこの例題集の設計。

## 未解決のまま残していること

- `EE.BITREV` の第 2 オペランド: 図は `ax`（アドレスレジスタ）、構文行は `as`、疑似コードは `as[15:0]` を
  **値**として使う。ex01 は 2 つのアドレスで走らせて生の 4 ワードを出すだけで、判定はログを見てから
  （`FFT_BIT_WIDTH` 特殊レジスタを設定する命令が命令一覧に見当たらないため、期待値を作れない）。
- `EE.VMULAS.*` のアキュムレータ書き込みが Table 1.7-2 の `def` に無い件（ex02 の実測サイクルから穴の
  大きさは測れる）。
- `EE.SRCMB.S16.QACC qu, as, 0` の `qu` への詰め方（疑似コードの後半が 16bit 飽和なのか丸めなのか
  読み切れていない）。QACC 経由の 8 並列を書くときに必要になるので、そのときに例題を足す。
